# PMS5003T on Waveshare V2

Source-checked 2026-09-28 against [Plantower PMS5003T specification PTQ3007-2015 V1.1, 2019-11-06](https://taoic.oss-cn-hangzhou.aliyuncs.com/8445/product/13260877853_1618968359000.pdf) and the [Waveshare V2 pin table](https://docs.waveshare.com/ESP32-S3-SIM7670G-4G/Arduino). The owner's image is a wiring proposal, not a measured board result.

| Sensor lead | Board lead | Notes |
| --- | --- | --- |
| VCC | 5 V, physical header pin 35 in the supplied image | Sensor supply 4.5–5.5 V; do not use 3V3 or VBAT |
| GND | GND, physical header pin 37 | Common return |
| TX | GPIO1, physical header pin 20 | ESP32 RX, 3.3 V logic |
| RX | GPIO2, physical header pin 16 | ESP32 TX, 3.3 V logic; this conflicts with MAX17048 SCL on V1, but the owner confirmed V2.0 |
| SET / RESET | Unconnected | Internal pull-ups permit active operation without host control |

Use 9600 baud, 8 data bits, no parity, one stop bit. The active frame is 32 bytes: header `42 4D`, length word `00 1C`, big-endian data, version/error at bytes 28/29, and checksum at 30/31 equal to the 16-bit sum of bytes 0–29. After sleep/wake, allow at least 30 seconds of stabilization before marking a frame valid. The existing logger's warm-up gate is uptime-based and would need revision if sensor sleep/reset is added.

| Frame bytes | PMS5003T meaning |
| --- | --- |
| 4–9 | CF=1 PM1 / PM2.5 / PM10, µg/m³ |
| 10–15 | Atmospheric PM1 / PM2.5 / PM10, µg/m³ |
| 16–23 | Counts per 0.1 L above 0.3 / 0.5 / 1.0 / 2.5 µm |
| 24–25 | Temperature, tenths of °C |
| 26–27 | Relative humidity, tenths of percent |

PMSA003 also has a 32-byte frame, but bytes 24–27 are counts above 5 and 10 µm there. The shared parser chooses a sensor model explicitly. A Waveshare telemetry schema must mark those two particle count fields null and place temperature/RH in their own fields; it must not silently reuse the CoreS3/PMSA003 dictionary or its `cores3-*` identifiers. No valid PMS5003T frames or environmental accuracy result has yet been measured on this board; the [diagnostic capture](bench-verified.md#diagnostic-flash-and-boot-2026-09-28) recorded zero frames.

## Silent fan / no frames

On 2026-09-28 the owner reported the fan was not running, alongside the zero-frame diagnostic capture. Check the supply and connector before changing UART code; a silent fan alone does not identify the fault.

1. Disconnect power before reseating or changing wiring. Check the sensor connector against the manufacturer's orientation drawing; cable colours and a mirrored connector view are insufficient to identify pin 1.
2. Sensor pins are **1 VCC, 2 GND, 3 SET, 4 RXD, 5 TXD, 6 RESET, 7/8 unused**. Keep SET, RESET and unused pins disconnected in this four-wire setup. SET low puts the sensor to sleep; RESET low holds it in reset.
3. With USB power connected, measure directly across sensor VCC/GND. Expect **4.5–5.5 V**; 3V3 and VBAT are unsuitable. Check the board's 5 V header pin and the cable connection separately if the sensor reading is low or absent. The supply must support the specified operating current, up to 100 mA.
4. Once power is correct and the fan runs, check sensor TX → GPIO1 and sensor RX → GPIO2, then capture at least 45 seconds. The diagnostic reports nulls until fresh valid frames pass its warm-up gate.

The running diagnostic has already booted through the WCH UART bridge without a button press. BOOT/RESET concerns the ESP32 download path; it is not a PMS fan enable. No change to the current DIP-switch configuration is required by the verified flashing path. A measured supply voltage or wiring photo is needed to narrow the remaining sensor fault.
